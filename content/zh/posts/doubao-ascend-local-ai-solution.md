## 为什么是「一套底座、双产品」

企业引入 AI Agent 时最常见的重复建设，是研发买一套、办公再买一套，模型网关、知识库、权限审计各配一份。这个方案的核心思路是**平台能力复用**：

| 对比维度 | 豆包 TRAE（Coding） | 豆包 Work |
|---|---|---|
| 主要用户 | 研发工程师、架构师、技术管理者 | 产品、运营、市场、销售、HR、财务等全职能员工 |
| 核心任务 | 代码生成、超级补全、Solo 全流程研发 | 文档、表格、PPT、数据分析、调研、任务自动化 |
| 工作空间 | IDE / CLI / 插件 + 企业代码上下文 | PC / Web / 移动端 + 项目空间 + 本地/云电脑执行 |
| 治理重点 | 代码不落地不训练、命令黑名单、MCP 白名单 | 资源 × Agent 双层管控、敏感操作确认、出口管控 |

两者共享：本地模型网关、RAG / 向量库、对象存储、身份权限（SSO / RBAC）、用量运营、审计日志，以及 **A卡 NPU 推理资源**。

## 总体业务架构：四层分层

```text
01 员工与入口      豆包 TRAE（IDE/CLI/插件） · 豆包 Work（PC/Web/移动端/飞书）
                    企业管理后台 · 自动化与开放接口（定时任务/Bot/API/MCP）
        ↓
02 双产品应用      Coding 应用域（AI Chat/CUE 补全/Solo/仓库索引/沙箱）
                    Work 应用域（工作任务/技能/连接器/伙伴/本地与云电脑执行）
        ↓
03 共享平台        Agent 运行时 · 模型网关 · 知识 RAG · 资产/技能库
                    身份与策略 · 审计与运营
        ↓
04 本地资源        企业系统与数据（代码仓库/CI-CD/OA/ERP/CRM/数据仓库）
                    A卡本地基础设施（鲲鹏 128C · A卡 910B · 双 CE / 存储）
```

**一次任务的数据流**：用户输入 → 上下文装配 → 身份与策略校验 → 本地推理（模型网关 / A卡 NPU）→ 工具执行（文件/浏览器/连接器/沙箱）→ 交付与审计。控制面统一经过「身份 → 权限密级 → 出口策略 → 敏感操作确认 → 内容安全 → 审计」；缺权限拒答或转人工，本地推理异常只降级到已批准模型，禁止未授权外发。

## 部署与推理架构要点

**私有化组网**（2000 人五节点参考）：终端 → 边界区（防火墙 HA + WAF/L7 负载均衡，HTTPS 443 终结于 VIP）→ 双 CE M-LAG（单交换机故障不中断）→ 3 个应用/RAG 节点 + 2 个 A卡推理节点；VLAN 按 AI-APP / AI-DATA / AI-MODEL / AI-STORAGE / AI-MGMT / OOB 分区，模型 API 走 mTLS。

**资源套餐**（附件数据，需 PoC 压测修正）：

| 企业规模 | 服务器 | 单台配置 | A卡 NPU 总量 | 高可用 |
|---|---|---|---|---|
| ≤500 人 | 2 台 | 鲲鹏 128C / 512GB / 1.5TB NVMe | 16 × 910B | 否 |
| 1000 人 | 3 台 | 同上 | 24 × 910B | 是 |
| 2000 人（参考组网） | 5 台 | 同上 | 16 × 910B | 是 |
| 3000 人 | 7 台 | 同上 | 24 × 910B | 是 |

**推理架构**以 GLM5.1 六机方案为示例：模型网关（鉴权/路由/限流/降级）→ 前缀与缓存路由（会话亲和 · Prefix Cache）→ **Prefill 集群（2 机，DP4·TP8·EP16）** 与 **Decode 集群（4 机，TP4·EP64）** 分离部署，配合 KV Cache 去碎片/前缀复用/量化压缩/跨节点卸载，以及 PD 分离、专家并行、投机解码等优化。参考指标：1120 研发用户 / 112 并发，TPOT 33ms（90% Prefix Cache 命中）。

## 安全与治理：资源 × Agent 双层管控

- **资源层**：企业身份与对象权限直接生效，文档/消息/审批继承平台安全域，水印 / DLP / 密级覆盖输入输出，租户隔离 + 传输存储加密。
- **Agent 层**：角色与可用场景定义、工具/MCP/连接器白名单、网络出口 URL/IP/CIDR 管控、沙箱执行与命令黑名单。
- **统一策略与审计**：允许 / 询问 / 拒绝三态决策，高风险操作二次确认，「谁 × Agent × 资源 × 动作」四要素记录，支持 Agent 视角与资源视角双向回溯。
- 关键原则：**AI 没有「专用超级账号」**，Agent 只能代表被授权用户访问资源；权限变更后 AI 侧访问范围同步收敛。

## 16:9 架构动画：两个完整示例

演示页内置双场景动画，每个场景都带一个真实任务示例，节点按阶段点亮、连线流动、任务步骤逐步打勾：

**豆包 Work Agent（办公场景）**——示例：*安排跨部门季度复盘会，并生成和分发会议纪要*
Planner（查日历→协调人→订会议室→整理纪要）→ Reasoning → Agent 核心循环（任务编排 / 流程控制 / 执行参数 / 等待审批的状态回环）→ Reflection（检查回执，失败重试或转人工）→ Function 汇总 → 输出会议安排与纪要摘要，产物归档可审计。

**豆包 TRAE Agent（研发场景）**——示例：*为订单服务新增「导出报表」接口，补齐单测并通过 CI*
Planner（定位模块→规划接口与测试→拆解到文件）→ Reasoning → 核心循环（文件级修改 / 沙箱执行 / MCP 白名单参数 / Diff 等待人工 Review）→ Reflection（测试失败重试、回滚或转人工）→ 输出变更摘要与验证结果。

两个场景的 Memory（记忆）、Tool（工具）、MCP（标准接入）与执行边界各不相同，但运行在同一套本地智能底座上：**本地模型服务 → A卡 NPU 推理池 → 知识 RAG → 对象存储 / 审计，数据不出企业域**。

## 落地路径与验收

实施分六阶段设门禁：调研与 PoC → 架构与 BOM → 环境部署 → 模型与数据适配 → 联合验收 → 分批上线与运营；每阶段有明确可验收产物，门禁不通过不进入下一阶段。验收覆盖产品功能、部署组网、模型性能（TPOT/TTFT/并发/稳定性）、数据与知识（权限过滤/引用溯源/事实校验）、安全治理与运维保障六大域。

两个需要提前锁定的事项：

1. **模型授权**：基础套餐不默认包含大模型权重与授权，需选择 SaaS Model Hub、企业自有或三方模型，并单独列项。
2. **身份生态**：豆包 Work 原生与飞书权限深度耦合，客户使用其他 IdP 时的适配范围需在 PoC 中验证。
